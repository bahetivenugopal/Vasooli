# Engine 1 — measured results

Every number on this page came out of an actual run and is reproducible from its
seed. Nothing here is rounded up, and the things that went badly are on the page
with the things that went well.

Reproduce any of it:

```bash
python scripts/root_cause_demo.py --batch-id <a fresh id>            # live provider
python scripts/root_cause_demo.py --batch-id <a fresh id> --deterministic
```

## The headline run

**Dataset** `pay-s42-d5db86f7` (589 attempts, 29–31 Aug 2026, seed 42)
**Run** `rc-demo-live-2`, seed 42, run clock `2026-08-31 18:23 UTC`
**Reasoning layer** Gemini `gemini-3.1-flash-lite`, prompt `diagnose_corridor` v1
**Razorpay** simulated mode (deterministic fixtures, ADR 0004)

| | |
| --- | --- |
| Payment attempts read | 589 |
| Failed attempts | 66 |
| Amount at risk | **₹5,25,206.00** |
| Amount recovered | **₹1,82,503.00** |
| Recovery rate | **34.75%** |

**Read that recovery rate carefully.** It is the money recovered by retrying
individual failed payments, sampled from the documented retry-success model in
`data/generators/configs/retry_success_model.json`. Those probabilities are
*ours*, not measured from production traffic — Phase 2's data card says so, and
it is the single biggest lever on this figure. What the number demonstrates is
that the loop runs end to end and is bounded; it is not a claim about how much
revenue this would recover from real traffic.

**The reroute contributes nothing to it.** The retry-success model has no route
dimension, so applying an uplift because traffic was rerouted would be inventing
the headline number rather than measuring it. The reroute is authorised,
recorded, bounded and expiring — and its effect on recovery is honestly zero in
this measurement.

### The false positive, reported in full

`netbanking × rt_nb_direct` (method_route), window 2026-08-31 01:01–07:01 UTC:
**57.1% success over 7 attempts against a 95.5% baseline, p = 0.0029.** Three
failures — one `ISSUER_UNAVAILABLE`, one `TECHNICAL_DECLINE`, one
`GATEWAY_TIMEOUT` — across three distinct customers.

Statistically it is a real drop. The generator did not inject anything there, so
it is a false positive and is counted as one. It is not argued away, and
tightening the threshold to remove it also removes the route-level true positive
— which is exactly the trade ADR 0007 documents rather than quietly making.

What happened next is worth noting as much as the detection itself: the model
diagnosed it as a route problem and recommended a reroute, and the **policy
engine refused** — `corridor-detection:RR3`, there is no alternate netbanking
route to send traffic to. The wrong detection did not become a wrong action. That
was luck rather than design, and the honest reading is in ADR 0006's consequences.

## An example diagnosis, verbatim from the trail

**Corridor** `HDFC × upi`, 31.6% success over 19 attempts against a 97.3%
baseline, p < 0.0001, ₹83,113 at risk, 13 distinct failing customers.

> The HDFC x UPI corridor shows a sharp drop in success rate to 31.58% compared
> to a 97.30% baseline, while comparable corridors like ICIC x UPI and SBIN x UPI
> remain healthy. Since 11 of the 13 failures are due to ISSUER_UNAVAILABLE, it
> strongly indicates a localized outage at the issuing bank rather than
> individual customer issues.

— `gemini-3.1-flash-lite`, prompt `diagnose_corridor` v1, `source: model`

Determination `systemic`, hypothesis `issuer_outage`, recommended
`reroute_traffic`. The policy engine permitted it under
`corridor-detection:RR2`, and the reroute was opened to `rt_upi_npci_b` with an
expiry six hours later (`corridor-detection:RR1`).

**Corridor** `netbanking × rt_nb_direct`. Model determination `systemic`,

## Graceful degradation

Three things were verified, two of them unforced.

**The confidence floor fired on its own.** On `card × rt_card_acq_2` the live
model returned its diagnosis with **confidence 0.55**, below the 0.6 floor
(`corridor-detection:DX1`). The answer was discarded and the deterministic
classifier ran instead, which reached `insufficient_evidence` and escalated. This
is the first observed case of the model reporting genuine uncertainty — Phase 1
had recorded it returning `1.0` on a clear-cut classification, and this is
evidence the confidence signal carries information rather than being ceremonial.

**A full run with no provider at all.** `--deterministic` forces every reasoning
task onto its fallback. The run completes, all three corridors are diagnosed,
1 abstention is raised, and every entry is audited `source: deterministic`:

| | live run | deterministic run |
| --- | --- | --- |
| Detections | 3 | 3 |
| Diagnoses | 2 systemic, 1 insufficient evidence | 2 systemic, 1 insufficient evidence |
| Reroutes authorised | 1 | 1 |
| Policy denials | 11 | 11 |
| Recovery rate | 34.75% | 34.75% |
| Entries `source: model` | 2 | 0 |

The recovery figures are identical because per-payment recovery is entirely
rule-driven — the model's judgment applies at the corridor level. That is worth
saying out loud rather than presenting the two runs as if the model earned the
recovery number.

**The response cache works.** A second live run served both model calls from
cache with zero live calls, so a pre-demo re-run costs no quota. One caveat found
in this phase: a result rejected by the confidence floor is **not** cached, so
that particular call is re-made on every run.

## What underperformed

Listed because a metric quietly omitted is worse than one reported with context.

1. **Precision is 64–67%.** One detection in three is not backed by ground truth.
   At this data volume that is the cost of catching the marginal route-level
   event at all; ADR 0007 shows the alternative and why it was not taken.
2. **Recall across seeds is 70%.** The route-level degradation is missed on three
   of five seeds. It is genuinely hard to see — the design intent from Phase 2 —
   but "missed" is the accurate word.
3. **Detection latency on the issuer rail is 9.5 hours.** Most of that is the
   minimum-baseline requirement: `corridor-detection:MV2` needs 20 prior attempts
   on the corridor, and on a three-day batch with no baseline carried in from
   previous days, the first hours are undetectable by construction. A real
   deployment would carry the baseline across batches. This one does not.
4. **The false-positive detection was still diagnosed as systemic.** The
   diagnosis layer is asked *why* a corridor degraded and is not given a way to
   say "it did not". It was refused for an unrelated reason. This should be fixed
   before the diagnosis layer is trusted more.
5. **Only 41 of 57 authorised retries reached the Razorpay client** — the 20 that
   succeeded, plus the 21 failures whose decline has a doc-verified upstream
   reason. The other 16 failures were recorded from the code already held,
   because round-tripping them through the client would normalize them to
   `UNKNOWN` and mislabel the failure. That is Phase 2's
   `simulate_failure_key: None` case working as documented, not a gap — but it is
   why the API-call count is smaller than the retry count, and anyone comparing
   the two should know that before assuming a bug.
